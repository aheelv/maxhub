一、方向说明

AI 编程与智能体是技术侧讨论热度最高的方向。斯坦福《2026 AI Index Report》显示，智能体在真实计算机任务上的成功率由约 12% 提升至约 66%，组织 AI 采用率升至 88%；技术社区的 2026 年 9 月热词观察中，AI 应用开发、AI 编程、AI Agent 与本地部署持续占据搜索量。相较前四类，其大众渗透率较低，主要面向开发者与进阶用户，因此排在第五。

本课把「智能体」落到可验证的工程含义上：不是接入一个外部平台，而是让 WorkBuddy 按需求生成程序、按测试用例运行、根据失败结果自主修订，并把「感知—判断—执行—校验」写成一份可配置的规则链。规则链在本地运行、可复现、可评分，不依赖任何额外账号或 API Key。

凡涉及外部智能体平台、连接器、云端发布的能力一律设为可选并明确标注「未启用」；主流程仅用 WorkBuddy 的对话、文件读写、命令执行与网页预览能力即可完整实现。

二、学习目标

  1. 能把模糊需求澄清为含输入、输出、规则、边界与验收口径的需求说明。
  2. 能用 WorkBuddy 生成一个零依赖的单文件网页工具，并在本地实际运行。
  3. 能用 12 个测试用例（含正常、边界、异常）驱动缺陷发现与至少一轮修复。
  4. 能理解并实现一份「感知—判断—执行—校验」的本地规则链配置，说明它与外部智能体平台的区别。

五、一站式流程

阶段从输入到成品
① 输入素材含 3 处模糊表述的需求说明 + 30 行含错报名数据 + 12 个测试用例 + 界面草图说明
② 定义层需求澄清（3 处模糊 → 可判定规则）→ 验收口径表 → 规则链 JSON（感知/判断/执行/校验）
③ 构建层生成单文件工具：CSV 导入 → 校验 → 去重 → 统计 → 结果表与导出；界面按草图实现

六、逐步操作指导（90 分钟）

步骤 1 · 0–6 分钟

素材核对与需求通读

目标：清点 8 份素材，列出需求中无法直接编码的模糊表述。

  1. 建立 第5课_小应用制作包/。
  2. 读取 01_需求说明书.md，标出至少 3 处模糊点（如「重复」「有效报名」「超容量」如何判定）。
  3. 写入 01_需求澄清清单.md（模糊点 / 为什么不能直接编码 / 拟确认的规则）。

可整段复制的提示词 / 能力输入：

读取「素材/第5课_智能体小应用/01_需求说明书.md」与「02_报名样例数据.csv」。列出至少 3 处无法直接编码的模糊表述，逐条写明：原文摘录、为什么不能直接编码（缺少什么判定条件）、你建议的可判定规则、以及该规则会影响 03_验收测试用例.csv 中的哪些用例号。同时清点素材目录 8 份文件是否齐全并输出核对表。不要替需求方拍板，建议规则要标注「待确认」。
项内容
输入需求说明书、样例数据、素材包
输出01_需求澄清清单.md + 素材核对表
WorkBuddy 能力WB-CHAT 对话与长文写作
替代路径若不足 3 处，按「输入格式、判定阈值、输出格式」三个维度再检查一遍，不得硬凑。
当场自检点≥3 处模糊点；每处有关联用例号；核对表 8 行。
步骤 2 · 6–16 分钟

需求澄清与验收口径

目标：把模糊点定为可判定规则，形成开发前冻结的口径表。

  1. 逐条把「待确认」转为确定规则（课堂情境下由学生本人作为需求方签核）。
  2. 写出 6 条明确规则 R1—R6：去重键、必填字段、学号格式、容量上限、时间先后、输出字段。
  3. 写入 02_验收口径表.md，并标注每条规则对应的测试用例号。

可整段复制的提示词 / 能力输入：

基于「01_需求澄清清单.md」，把每条「待确认」规则确定为可执行规则，输出 02_验收口径表.md：规则编号 R1—R6 / 规则描述（须可写成 if 判断）/ 判定输入字段 / 命中后的动作 / 关联测试用例号 / 决策人（本课填「学生本人（课堂演练）」）。至少覆盖：① 重复报名的去重键与保留策略；② 必填字段与缺失处理；③ 学号格式合法性；④ 活动容量上限与超额处理；⑤ 同一人多次报名的先后判定依据；⑥ 输出结果的字段与排序。规则之间不得互相矛盾；若某条与 03_验收测试用例.csv 的期望输出冲突，明确指出冲突并调整规则描述，不得修改测试用例。
项内容
输入需求澄清清单、测试用例
输出02_验收口径表.md
WorkBuddy 能力WB-FILE 本地文件读写
替代路径规则冲突时以测试用例的期望输出为准，调整规则描述并在表中记录调整原因。
当场自检点R1—R6 均可写成 if 判断；每条关联用例号；无相互矛盾。
步骤 3 · 16–26 分钟

设计本地规则链（智能体式编排）

目标：把需求写成「感知—判断—执行—校验」四段可配置规则链。

  1. 生成 03_规则链.json：四段各有 steps，每段含 id、type、rule_ref、input、output、on_error。
  2. 明确写出：这是本地可复现的规则链，不连接外部智能体平台。
  3. 写入 04_规则链说明.md，解释每段的职责与失败处理。

可整段复制的提示词 / 能力输入：

依据「02_验收口径表.md」生成 03_规则链.json，结构为 {"name":...,"mode":"local-deterministic","stages":[{"stage":"感知","steps":[...]},{"stage":"判断",...},{"stage":"执行",...},{"stage":"校验",...}]}。每个 step 含 id、desc、rule_ref(引用 R1—R6)、input、output、on_error。四段职责：感知=读取与解析 CSV 并登记行数；判断=按规则逐行分类（有效/重复/缺字段/格式错/超额）；执行=去重、统计、生成结果表；校验=合计校验与用例断言，失败时回滚到上一步并给出错误行号。另写 04_规则链说明.md：说明这是「本地确定性规则链」，用于演示智能体的感知—判断—执行—校验循环，不连接任何外部智能体平台或大模型 API；逐段解释职责、输入输出与失败处理；写明它与真实智能体平台（工具调用、记忆、权限）的三点区别。不得把本地规则链描述为已接入外部平台。
项内容
输入验收口径表
输出03_规则链.json、04_规则链说明.md
WorkBuddy 能力WB-FILE 本地文件读写
替代路径规则链以 JSON 表达即可，不要求引入工作流引擎或外部依赖。
当场自检点四段齐全；每个 step 引用有效 rule_ref；JSON 可解析；「本地确定性」表述明确。
步骤 4 · 26–42 分钟

生成单文件报名统计工具

目标：让 WorkBuddy 生成一个可直接在浏览器运行、无外部依赖的工具。

  1. 按 04_界面草图说明.md 与 R1—R6 生成 05_报名统计工具.html。
  2. 功能：粘贴/上传 CSV → 规则链四段执行 → 结果表 + 分类统计卡 + 错误行明细 → 导出结果 CSV。
  3. 在预览面板打开，用 02_报名样例数据.csv 实际跑一次，确认 30 行被读取。

可整段复制的提示词 / 能力输入：

请生成一个单文件网页工具「05_报名统计工具.html」，零外部依赖、零网络请求，双击即可运行。实现「02_验收口径表.md」的 R1—R6 与「03_规则链.json」四段流程。界面按「04_界面草图说明.md」分区：① 输入区（文件选择 + 文本粘贴框 + 「开始处理」按钮 + 示例数据按钮）；② 规则链状态区（感知/判断/执行/校验 四段，逐段显示状态与耗时/行数）；③ 统计卡（总行数、有效数、重复数、缺字段数、格式错数、超容量数，六个数字必须与明细一致）；④ 结果表（输出字段与排序按 R6）；⑤ 错误行明细（行号 / 错误类型 / 原始行内容）；⑥ 「导出结果 CSV」按钮。要求：CSV 解析自行实现（支持带引号字段与 UTF-8 BOM）；所有判断必须可追溯到 R 编号；界面给出明确状态反馈；中文 UTF-8；无控制台报错。只输出完整 HTML 代码，不要省略片段。
项内容
输入验收口径表、规则链、界面草图、样例数据
输出05_报名统计工具.html
WorkBuddy 能力WB-HTML 网页与应用构建、预览
替代路径若文件选择受浏览器限制，以「文本粘贴 + 示例数据按钮」为主路径，文件选择为附加能力，不影响验收。
当场自检点预览面板实际打开；示例数据 30 行被读取；四段状态依次点亮；六个统计数可见。
步骤 5 · 42–56 分钟

12 个测试用例实跑

目标：用测试驱动验证，而不是只看界面「看起来能用」。

  1. 让 WorkBuddy 把网页中的核心判断逻辑抽成可在命令行运行的同名函数（或写一个等价测试脚本）。
  2. 对 03_验收测试用例.csv 的 12 个用例逐个实跑，输出 06_测试记录.csv。
  3. 统计 PASS/FAIL，并对每个 FAIL 记录实际输出与期望输出。

可整段复制的提示词 / 能力输入：

读取「03_验收测试用例.csv」。用命令执行能力对「05_报名统计工具.html」中的核心判断逻辑做一次等价复现测试（可抽取核心函数为独立 Node/Python 脚本，但必须与网页使用同一套 R1—R6 规则与阈值）。对 12 个用例逐个实跑，输出 06_测试记录.csv：用例号,类型(正常/边界/异常),输入摘要,期望输出,实际输出,PASS或FAIL,失败原因,关联规则编号。要求：数字与判定必须由实际运行结果填写，不得凭代码目测；按 正常/边界/异常 三类分别统计通过率；列出全部 FAIL 的用例号。若网页逻辑与测试脚本难以共享代码，请说明口径并附一份 07_核心逻辑说明.md，保证两者规则一致。
项内容
输入测试用例、网页工具、验收口径表
输出06_测试记录.csv（+ 可选 07_核心逻辑说明.md）
WorkBuddy 能力WB-CMD 命令执行与数据处理
替代路径若无法抽取共享代码，改用浏览器内测试面板：在网页中内置「运行 12 用例」按钮并把结果导出为 CSV，结论同样必须来自实际运行。
当场自检点12 行测试记录；三类通过率由脚本计算；FAIL 均有实际输出与原因。
步骤 6 · 56–68 分钟

缺陷记录与一轮修复

目标：针对 FAIL 定位原因、实际改代码、回归全部用例并给出前后对比。

  1. 生成 08_缺陷记录.csv：编号/用例号/现象/根因/关联规则/修复动作/修复后状态。
  2. 修改 05_报名统计工具.html，回归 12 个用例，输出「修复前 → 修复后」对比。
  3. 若修复导致新 FAIL，记录并回退或继续修复。

可整段复制的提示词 / 能力输入：

依据「06_测试记录.csv」的 FAIL 项，生成 08_缺陷记录.csv（编号/用例号/现象/根因/关联规则编号/修复动作/修复后状态）。随后实际修改「05_报名统计工具.html」中的对应逻辑，重新对 12 个用例做一次全量回归，输出 09_回归结果.csv 与「修复前 / 修复后」对比表（总通过数、三类通过率、新增 FAIL 数）。硬性要求：不得为了通过测试而把期望输出硬编码进程序；修复必须落在 R1—R6 的规则实现上；若出现新增 FAIL，必须记录并继续修复或明确回退该改动。对比表数值来自脚本，不得手工填写。
项内容
输入测试记录、网页工具、验收口径表
输出08_缺陷记录.csv、09_回归结果.csv、修订后的网页工具、对比表
WorkBuddy 能力WB-CMD 命令执行与数据处理
替代路径若首轮 12 用例全 PASS，则改为主动构造 2 个新的边界用例（如空文件、全重复）并实跑，把结果与处理写入缺陷记录，不得虚报「发现并修复了缺陷」。
当场自检点对比表有前后数值；至少 1 轮真实修改与回归；未硬编码期望输出。
步骤 7 · 68–78 分钟

README 与规则链讲解
