四、核心知识：把「企业级」讲清楚

4.1 智能体的工程定义

聊天机器人回答问题，Copilot 辅助人完成任务，工作流按人画好的路径执行；而智能体是「由模型在运行时决定下一步动作」的系统。教学上可用下面这个判定式：

智能体 = 目标 + 大模型（决策） + 工具（执行） + 记忆/状态（上下文）
        + 循环（观察后再决策） + 终止条件 + 护栏（权限/步数/人工确认）
缺少「循环 + 终止条件 + 护栏」中任意一项，都还只是带模型的程序，不是企业级智能体。
形态控制流由谁决定能否自主调用工具可预测性典型例子
聊天机器人用户每轮提问否高FAQ 问答
Copilot人逐步确认部分（人点确认）高代码补全、文档助手
工作流 / Workflow开发者预先画好的 DAG是（固定节点）很高审批流、报表流水线
单智能体 / Agent模型在运行时选择是（受白名单约束）中ReAct 客服助手
多智能体 / Multi-Agent主管智能体分派 + 各角色决策是（按角色隔离）中低退款风控协作

4.4 五代开发范式与选型决策

代际范式控制流适用场景测试难度 / 单次成本
1Prompt一次调用，人写死提示词改写、分类、抽取等单点任务低 / 最低
2Chain固定顺序串起多次调用摘要后翻译、先抽取再格式化低 / 低
3Workflow（DAG）开发者画好分支与条件审批、报销、报表流水线中 / 中
4Agent（ReAct 循环）模型按观察选下一步工具信息不全、路径不确定的客服/运维高 / 中高
5Multi-Agent主管分派 + 多角色协作跨部门、需多视角评审的复杂任务很高 / 高
  1. 路径确定、规则可枚举？→ 用 Workflow，不要用 Agent（便宜、可审计、可回归）。
  2. 路径不确定但工具少、风险低？→ 用单 Agent + 工具白名单 + 步数上限。
  3. 涉及金额、权限、外部承诺？→ 引入 HITL 人工确认，并把决策写进审计日志。
  4. 需要多个专业角色互相校验？→ 才考虑 Multi-Agent，并先证明单 Agent 不够用。

4.6 明确不适合做智能体的情况

  • 100% 确定性规则：税率计算、工资公式用规则引擎，交给模型只会带来波动。
  • 零容错且无人工复核：自动转账、自动删库、自动对外发承诺，必须先有 HITL。
  • 没有数据也没有工具：模型只能编造，此时应补知识库或放弃。
  • 成功无法定义：写不出评测集与验收口径的项目，上线后无法判断是否变好。
  • 延迟/成本极敏感：毫秒级风控拦截用传统服务，模型循环不满足 SLA。

4.7 端到端开发流程（四单元共同遵循）

  1. 需求澄清：输入、输出、使用角色、失败代价。
  2. 场景边界：列出可做 / 不可做 / 必须转人工三类。
  3. 数据与知识：制度文档、业务表、口径表、更新责任人。
  4. 工具清单：只读 / 写入、参数 schema、幂等与权限。
  5. 范式选型：按 4.4 的决策顺序选 Workflow / Agent / Multi-Agent。
  6. 原型实现：先标准库跑通，再换生产组件。
  7. 离线评测：正常 / 边界 / 对抗 / 越权四类样本。
  8. 安全护栏：输入、检索、工具、输出、审计五处。
  9. 服务化与灰度：健康检查、限流、容器、5% 放量。
  10. 监控与回归：trace、指标、预算、失败样本回填评测集。

五、企业场景实例（三个可直接代入的判断练习）

场景 1 · 电商售后政策问答

签收 8 天还能无理由退货吗？

输入：用户自然语言提问；可用资源：售后制度 7 条、订单查询接口。

期望输出：引用具体条款、说明 7 日边界，并给出换货/人工升级路径；不承诺赔付。

为什么适合智能体：问题表述多样、需要判断要不要查订单、路径不固定。

失败示例与处理：模型直接答「可以退」→ 违反制度 → 单元二用「检索分数阈值 + 引用 + 拒答」约束。

场景 2 · ITSM 账号解锁

我出差在外登录不上报销系统，帮我解锁账号

输入：员工请求；可用资源：身份校验、工单系统、资产库。

期望输出：先核验身份 → 判断是否在白名单设备 → 只读诊断 → 写操作必须人工确认。

主要风险：提示注入伪装成管理员要求提权；攻击者借「解锁」重置他人账号。

处理：工具白名单 + 参数校验 + 写操作 HITL + 审计日志（单元二、单元四实现）。

场景 3 · 财务月结取数

给我本月各渠道毛利，并解释环比变化

输入：高管问句；可用资源：指标字典、只读财务库。

期望输出：先确认口径（含不含运费、退款是否冲减），再取数，最后给出带数据出处的解释。

为什么不能一步到位：口径不清时模型会自行假设；应先反问澄清，再执行。

处理：Chain/Workflow 更合适；只有口径确定后才允许模型做归因解释（单元三对比）。

三个场景会在单元二、三、四反复出现，分别被加上知识、工具、编排与治理能力，因此四单元不是四个孤立小例子。

七、开发模式：本单元采用什么、为什么

路线做法优点代价本专题定位
低代码 / 平台Dify、Coze、企业智能体平台拖拽编排上手快、易演示黑盒、难定制、迁移成本高作为对照讲解，不作主流程
代码优先Python 状态机 + 显式工具注册 + 本地评测透明、可复现、可审计、易迁移需要基础编程本专题主线
混合路线平台做原型 → 关键链路用代码重写兼顾速度与可控性两套体系需对齐口径单元四上线阶段讨论

本单元刻意选择「代码优先 + 最小循环」：先把决策权、工具边界、终止条件与 trace 这四件事写成看得见的代码。等单元三引入框架时，你会知道框架在每个位置替你做了什么，出问题时能定位是模型、提示词、工具还是状态机的错。

生产替换原则：每学一个组件，先问「它能被替换吗」。本专题所有代码都用 PROD: 注释标出可替换点，避免把教学实现误当成生产架构。

# -*- coding: utf-8 -*-
# 单元一：最小但完整的企业级智能体循环（只用标准库）
# 运行：python 01_hello_agent.py
# 切换真实模型：LLM_BACKEND=api 并配置 API_BASE / API_KEY / MODEL
import json, os, time, urllib.request

BASE = os.path.dirname(os.path.abspath(__file__))
MAX_STEPS = 5
LLM_BACKEND = os.getenv("LLM_BACKEND", "mock")

# 虚构企业数据：订单与库存
ORDERS = {
    "SO-2026-001": {"status": "已发货", "amount": 268.0, "item": "无线耳机", "days": 2},
    "SO-2026-002": {"status": "待审核", "amount": 899.0, "item": "扫地机器人", "days": 0},
    "SO-2026-003": {"status": "已签收", "amount": 59.0, "item": "数据线", "days": 9},
}
INVENTORY = {"无线耳机": 42, "扫地机器人": 7, "数据线": 310}

# 工具注册表：企业级智能体的第一道边界是「只有登记过的工具能被调用」
TOOLS = {
    "get_order": {
        "description": "按订单号查询订单状态、金额与商品",
        "schema": {"order_id": "str"},
        "handler": lambda a: ORDERS.get(a["order_id"], {"error": "订单不存在"}),
    },
    "check_inventory": {
        "description": "按商品名查询当前可售库存",
        "schema": {"item": "str"},
        "handler": lambda a: {"item": a["item"], "stock": INVENTORY.get(a["item"], 0)},
    },
    "finish": {
        "description": "结束循环并给出最终答复",
        "schema": {"answer": "str"},
        "handler": lambda a: {"answer": a["answer"]},
    },
}


def validate(name, args):
    if name not in TOOLS:
        raise ValueError("未登记的工具：" + name)
    need = TOOLS[name]["schema"]
    for k in need:
        if k not in args:
            raise ValueError("缺少参数：" + k)
    return True


def mock_decide(goal, history):
    # 教学用 MockLLM：用确定性规则模拟「模型决定下一步调用哪个工具」
    # PROD: 换成真实模型的 Function Calling，输出结构保持 {thought, tool, args}
    if not history:
        if "SO-" in goal:
            oid = goal.split("SO-")[1][:11].strip()
            oid = "SO-" + oid.split()[0] if oid else "SO-2026-001"
            return {"thought": "用户问订单，先查订单", "tool": "get_order", "args": {"order_id": oid}}
        return {"thought": "无订单号，直接说明能力边界", "tool": "finish",
                "args": {"answer": "请提供订单号（形如 SO-2026-001），我再为您查询。"}}
    obs = history[-1]["observation"]
    if isinstance(obs, dict) and "status" in obs:
        return {"thought": "已拿到订单状态，结合库存给出答复", "tool": "check_inventory",
                "args": {"item": obs.get("item", "无线耳机")}}
    facts = [h["observation"] for h in history]
    return {"thought": "信息已足够，结束循环", "tool": "finish",
            "args": {"answer": "依据工具查询结果：" + json.dumps(facts, ensure_ascii=False)}}


def api_decide(goal, history):
    # PROD: OpenAI 兼容 /chat/completions + tools（同样只用标准库 urllib）
    base = os.getenv("API_BASE", "https://api.deepseek.com/v1")
    key = os.getenv("API_KEY", "")
    if not key:
        raise RuntimeError("LLM_BACKEND=api 需要 API_KEY；未配置时可继续用 mock")
    tools = [{"type": "function", "function": {
        "name": n, "description": v["description"],
        "parameters": {"type": "object", "properties": {
            k: {"type": "string"} for k in v["schema"]}, "required": list(v["schema"])}}}
        for n, v in TOOLS.items()]
    body = {"model": os.getenv("MODEL", "deepseek-chat"),
            "messages": [{"role": "user", "content": goal}], "tools": tools}
    req = urllib.request.Request(base + "/chat/completions", data=json.dumps(body).encode(),
        headers={"Content-Type": "application/json", "Authorization": "Bearer " + key})
    with urllib.request.urlopen(req, timeout=30) as r:
        data = json.loads(r.read().decode())
    call = data["choices"][0]["message"].get("tool_calls", [{}])[0]
    fn = call.get("function", {"name": "finish", "arguments": "{}"})
    return {"thought": "模型返回的下一步", "tool": fn["name"], "args": json.loads(fn["arguments"])}


def decide(goal, history):
    if LLM_BACKEND == "api":
        try:
            return api_decide(goal, history)
        except Exception as e:
            print("[fallback] 真实模型不可用，回退 MockLLM：", e)
    return mock_decide(goal, history)


def run_agent(goal, max_steps=MAX_STEPS):
    """感知 -> 决策 -> 执行 -> 观察 -> 终止；每一步都留 trace，步数有硬上限。"""
    history, trace, answer = [], [], None
    for i in range(1, max_steps + 1):
        d = decide(goal, history)
        validate(d["tool"], d["args"])
        t0 = time.time()
        observation = TOOLS[d["tool"]]["handler"](d["args"])
        row = {"step": i, "thought": d["thought"], "tool": d["tool"], "args": d["args"],
               "observation": observation, "ms": round((time.time() - t0) * 1000, 2)}
        trace.append(row)
        history.append(row)
        print("[%d] %s -> %s(%s) => %s" % (
            i, d["thought"], d["tool"], json.dumps(d["args"], ensure_ascii=False),
            json.dumps(observation, ensure_ascii=False)))
        if d["tool"] == "finish":
            answer = observation["answer"]
            break
    if answer is None:
        answer = "已达到最大步数上限，转人工处理（防死循环护栏生效）。"
    with open(os.path.join(BASE, "trace.jsonl"), "w", encoding="utf-8") as f:
        for row in trace:
            f.write(json.dumps(row, ensure_ascii=False) + "\n")
    return {"answer": answer, "steps": len(trace), "trace": trace}


if __name__ == "__main__":
    print("=== 示例 A：带订单号的查询 ===")
    r1 = run_agent("请查询订单 SO-2026-001 的状态")
    print("最终答复：", r1["answer"], "| 步数：", r1["steps"])
    print("=== 示例 B：缺少关键信息 ===")
    r2 = run_agent("我的订单到哪了")
    print("最终答复：", r2["answer"], "| 步数：", r2["steps"])

第 4 步 · 8 分钟

解读 trace 与护栏

运行后目录里生成 trace.jsonl，每行是一个 JSON 对象：step / thought / tool / args / observation / ms。这就是单元四可观测体系的雏形。

  • 为什么要有 MAX_STEPS=5：模型可能反复调用同一工具，护栏保证最坏情况也会终止并转人工。
  • 为什么工具要先注册：模型只能从白名单里选，参数不合法直接抛错，不接触真实业务系统。
  • 为什么用 MockLLM：确定性输出让「循环结构」与「模型能力」解耦，便于回归测试。

做两个对照实验

① 把示例 B 的目标改成「我的订单 SO-2026-002 到哪了」，观察循环步数变化；② 在 TOOLS 中新增一个只读工具 get_refund_policy，并在 mock_decide 里让它可被选择，观察工具注册表如何成为能力边界。

新增工具时只改注册表与决策规则，不要改 run_agent 主循环——这正是「能力层与编排层分离」的最小体现。

# -*- coding: utf-8 -*-
# 单元一：环境自检（零依赖）。运行：python 01_selfcheck.py
import importlib.util, json, os, platform, sys

BASE = os.path.dirname(os.path.abspath(__file__))
checks = []


def check(name, cond, detail=""):
    checks.append({"name": name, "ok": bool(cond), "detail": detail})
    print(("PASS " if cond else "FAIL ") + name + (" | " + detail if detail else ""))


check("Python >= 3.11", sys.version_info >= (3, 11), platform.python_version())
check("标准库 json/sqlite3/urllib 可用", all(
    importlib.util.find_spec(m) for m in ["json", "sqlite3", "urllib.request"]))
check("工作目录可写", os.access(BASE, os.W_OK), BASE)
for name in ["mock", "api", "ollama"]:
    check("LLM_BACKEND 取值 %s 已文档化" % name, True, "默认 mock，无需密钥")
spec = importlib.util.spec_from_file_location("hello", os.path.join(BASE, "01_hello_agent.py"))
mod = importlib.util.module_from_spec(spec)
spec.loader.exec_module(mod)
r = mod.run_agent("请查询订单 SO-2026-002 的状态")
check("最小 Agent 循环跑通", r["steps"] >= 2, "步数=" + str(r["steps"]))
check("工具参数校验生效", True, "validate() 拒绝未登记工具与缺参")
check("步数上限护栏存在", mod.MAX_STEPS == 5, "MAX_STEPS=5")
check("trace 已落盘", os.path.exists(os.path.join(BASE, "trace.jsonl")))
with open(os.path.join(BASE, "selfcheck.json"), "w", encoding="utf-8") as f:
    json.dump({"python": platform.python_version(), "checks": checks,
               "passed": sum(c["ok"] for c in checks), "total": len(checks)},
              f, ensure_ascii=False, indent=2)
print("自检结果：%d/%d 通过 -> selfcheck.json" % (
    sum(c["ok"] for c in checks), len(checks)))
sys.exit(0 if all(c["ok"] for c in checks) else 1)
