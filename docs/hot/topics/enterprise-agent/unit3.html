核心知识 · 三种范式对照

复杂度递增，但并非越复杂越好；先用可预测的固定流程覆盖可枚举规则。

范式决策者LangChain 实现优点代价
Workflow开发者预先画好 DAGRunnableLambda + RunnableBranch可预测、易测试、成本低规则需可枚举
ReAct Agent模型按观察自主选工具create_tool_calling_agent + AgentExecutor适应未见过的问法步数、成本、结果不稳定
Multi-AgentSupervisor 分配角色多个 Runnable 角色 + 汇总函数职责分离、便于审计延迟与 token 成本更高
Plan-and-Execute、Reflection 属于在 ReAct 上叠加「先规划 / 再自检」的策略；生产用 LangGraph 状态图 + checkpoint 承载，可中断并恢复人工审批。

单元 3 · 编排与开发范式 · 第 5 / 13 页

逐步开发 ① · 固定工作流

分流规则写进 RunnableBranch，每一步输入输出都是确定的。

unit3/03_workflow.py · 第 1—28 行
# -*- coding: utf-8 -*-
"""单元三 · Workflow：开发者画好的固定 DAG，最便宜、最可回归。"""
import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parents[1]))
from common.lc import tickets

from langchain_core.runnables import RunnableBranch, RunnableLambda

validate = RunnableLambda(lambda t: dict(t, valid=bool(t.get("ticket_id"))))
route = RunnableBranch(
    (lambda t: t["risk"] == "high" or t["amount"] >= 2000,
     RunnableLambda(lambda t: dict(t, decision="转人工审批", steps=3))),
    (lambda t: t["days"] > 7 and t["type"] == "无理由退货",
     RunnableLambda(lambda t: dict(t, decision="超出7日，改换货或转人工", steps=3))),
    RunnableLambda(lambda t: dict(t, decision="按制度自动受理", steps=2)),
)
workflow = validate | route

for t in tickets():
    r = workflow.invoke(t)
    print("  %-5s %-12s -> %s" % (r["ticket_id"], r["type"], r["decision"]))
print("\n特点：路径固定、可预测、可写单元测试；适合规则可枚举的场景。")


def run(t):
    return workflow.invoke(t)
运行结果示例：T012 越权赔付请求 → 转人工审批。特点：路径固定、可预测、可写单元测试，适合规则可枚举的场景。

逐步开发 ③ · Supervisor 多角色

把「受理 / 风控 / 主管」拆成独立 Runnable，由 Supervisor 依据风险分派并汇总。

unit3/03_multi_agent.py · 第 1—28 行
# -*- coding: utf-8 -*-
"""单元三 · Supervisor 多角色：按风险把工单分派给售后/风控，再汇总。"""
import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parents[1]))
from common.lc import tickets

from langchain_core.runnables import RunnableBranch, RunnableLambda

售后 = RunnableLambda(lambda t: {"role": "售后专员", "意见": "符合制度，可受理", "ticket": t["ticket_id"]})
风控 = RunnableLambda(lambda t: {"role": "风控专员", "意见": "金额较大/越权，需人工复核", "ticket": t["ticket_id"]})
主管 = RunnableBranch(
    (lambda t: t["risk"] == "high" or t["amount"] >= 2000, 风控),
    售后,
)
汇总 = RunnableLambda(lambda x: dict(x, 结论=("转人工" if x["role"] == "风控专员" else "自动受理")))
crew = 主管 | 汇总

for t in tickets()[:6]:
    r = crew.invoke(t)
    print("  %-5s risk=%-4s -> %s / %s / %s" % (
        r["ticket"], t["risk"], r["role"], r["意见"][:12], r["结论"]))
print("\n注意：先证明单 Agent 不够用，再引入多角色；多角色成本与不确定性更高。")


def run(t):
    return crew.invoke(t)

核心知识 · 选型决策树

判断选择理由
规则可枚举、结果必须一致？Workflow可预测、单测容易、成本最低
用户问法无法预先穷举？ReAct Agent由模型按观察选择工具
需要角色分离、审批链或会签？Multi-Agent / LangGraph职责与状态可追踪
需要暂停等待人工、崩溃后恢复？LangGraph + checkpointHITL interrupt 与状态持久化
MCP 负责「工具怎么接」，A2A 负责「智能体之间怎么通信」，它们不改变编排选型的判断依据。

逐步开发流程与运行结果

  1. 加载 12 条工单，先跑 03_workflow.py 建立基线。
  2. 跑 03_react_agent.py，检查 intermediate_steps 是否真的查了制度与订单。
  3. 跑 03_multi_agent.py，观察高风险工单的分派。
  4. 跑 03_compare.py 生成对照报告。
  5. 写一段选型结论：指定场景 + 选择 + 依据数据。
四个脚本均已在离线环境实跑通过；对照报告含 12 条工单。
